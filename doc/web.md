## 1. 生成と配信

`scripts/build_web_map.py` → `docs/map2d/`、`docs/map3d/`、`docs/globe/`（GitHub Pages、master の `/docs`）

```bash
uv run python scripts/build_web_map.py data/processed/umap2d_nn15_md0.1.parquet
uv run python scripts/build_web_map.py data/processed/umap3d_nn15_md0.1.parquet
uv run python scripts/build_web_map.py data/processed/umapsphere_nn15_md0.0_sp0.3.parquet
```

入口 `docs/index.html` は手書き。背景の点群画像は `scripts/make_hero.py`、アイコン（favicon／PWA／apple-touch）は
`scripts/make_icon.py`、SNS プレビュー画像は `scripts/make_ogp.py` で生成する。検索エンジン・AI 向けに JSON-LD、
`robots.txt`、`sitemap.xml`、`llms.txt` を置く。

## 2. 構造（座標・共有シャード）

自己完結 HTML（約 130MB）は GitHub の 100MB 制限を超えるため、データを外に出した：

- `index.html`（約 90KB、Plotly.js は CDN）
- `points.bin`：座標を各軸 int16 に量子化（分解能は値域/65535、1 ピクセル未満）。トレース順（描画順）に連続配置。
  続けて「描画順 → 課題番号順の通し番号（uid）」の対応表（uint32）、最後に点ごとの色（sRGB 各 1 バイト、v1.3〜）を同梱。
- `docs/shards/NNN.json`：タイトル・キーワード・種目などを **課題番号順** に 2,048 件ずつ 101 片に分割。
  描画順はビューごとに違う（2D/3D は大区分×種目、球面は大区分×乱数 16 組）が、詳細データは 1 セットを 3 ビューで共有し、
  各ビューは対応表で引く。同じ URL なのでブラウザキャッシュがビュー間で効き、切り替え時に再読み込みしない（v1.1）。
  `kaken_id` は「KAKENHI-<種別>-<課題番号>」に分解できることを検証済みで、種別コードだけ持つ。

**二段階読み込み**：①`points.bin` をプログレスバー付きで取得して描画（実測 1.5 秒）、
②シャードを背景で先読みし、完了で検索を有効化（実測 8.4 秒）。未取得片へのホバーはその片だけ即時取得。
1 閲覧の転送量は約 20MB（シャードは gzip 配信）。2 回目以降は端末保存（§6）から読む。

## 3. トレース設計と Plotly 3D の制約

- 2D／3D のトレースは **大区分 × 種目**。種目フィルタはトレースの表示切替なのでデータ転送なしで速い。
- 点の色は点ごとの配列（`marker.color` に `rgb(...)` 文字列の配列。`points.bin` の RGB から起動時に作る）。トレースの `color` は
  大区分の代表色（所属課題の平均色）で、Plotly 凡例とスマホのシートの色見本にだけ使う。カード・ツールチップの縁と見出しは点自身の色。
  `POINT_COLOR=dai` で従来のトレース単色に戻せる（比較用）。
- **Plotly の 3D 判定はオブジェクト番号を 8 ビットで持ち、トレース数が 255 を超えるとホバー・クリックが効かなくなる**。
  球面はこの制約に当たったため、トレースを「大区分 × 乱数 16 組」に統合し（222 本）、種目はシャード行に持たせた
  （球面は種目フィルタ非対応）。
- 球面の点を不透明にすると gl-scatter3d の不透明経路が半透明の 3〜6 倍遅い。半透明にすると重なりの最上層が
  描画順に偏って色が嘘になるので、各点を乱数で組に分け、組ごとに大区分の描画順を回転させて交互に描く。
- 小さな半透明の点は画素中心を覆わず約 3 割が「下地」判定になる。カメラ行列で全点を投影して最近傍を探す
  自前判定（`nearestGid3d`、投影誤差 1px 未満）で補完する。

## 4. 操作（PC・タッチ）

- Plotly の 2D はタッチのピンチに対応しないため自前実装。
- 3D／球面は Plotly にタッチイベントを一切渡さず、カメラを自前で計算して `relayout` する
  （1 本指＝自由回転、2 本指＝拡大縮小、3D のみ移動、球面は中心固定）。Plotly のタッチ処理と競合させると
  離した瞬間に向きが戻る不具合が実機で起きた。
- 回転には慣性がある（離す直前 150ms の指速度、時定数 500ms の指数減衰、次のタッチで停止）。
- 点の選択：PC もタッチも、点をクリック／タップ → カード → カードのどこをクリックしても KAKEN（v1.2 で PC もカード方式に統一）。
  PC はホバーで概要も出す。カードに「リンクをコピー」
  （本物の `<a target=_blank>`。iOS のポップアップ制限と PWA で確実に開くため）。
  3D／球面のタップ位置判定は Plotly を使わず `nearestGid3d` で同期に決める。
- 地図を動かしても選択は消えず、リング（PC はカードも）が点に追随する。gl3d はカメラ行列の更新が描画側で遅れるので、
  移動後に数回（80/280/680ms）置き直す。球面の裏側に回った点はリングを隠す。
- 検索結果や URL から課題を開くと**フライ・トゥ**（全体図の上でリングとカードを出してから 1.2 秒で寄る。2D は範囲を対数補間、
  3D は注視点を点に移して寄る、球面は視線方向を大円に沿って補間）。カードの「全体 ⇄ 周辺」で行き来できる。
- タッチの 1 本指回転の感度は「視点から面（球面）／注視点（3D）までの距離」に比例させ、寄るほど弱くする。慣性も同じ感度。
- Plotly のカメラ座標（eye/center）は「データ座標 × dataScale に scene の model 行列を掛けた空間」。model を掛け忘れると
  3D で注視点がずれる（球面は箱が原点対称なので偶然合う）。
- iOS Safari は 16px 未満の入力欄にフォーカスすると画面を自動拡大するので、タッチ端末では検索欄を 16px にする。
- 狭幅では検索欄が先に縮み、「操作」は羅針盤メニューの末尾へ。大区分・種目は同じ部品のボトムシート（行タップで表示切替、すべて表示／非表示）。

## 5. 課題ごとの URL

`…/map2d/?award=19K16373` のように課題番号を付けて開くと、その課題を選択した状態で表示する。名簿（共有シャード）が
課題番号順なので、各片の先頭番号（`M.shardFirst`、101 個）で二分探索して該当する 1 片だけ読み、行番号 → uid → gid
（`points.bin` 同梱の対応表の逆引き）で点を特定する。SNS のプレビュー画像は URL ごとに変えられない（静的サイト）。
カードのアイコンで URL のコピー（対応端末では共有）ができ、カードを開くとアドレスバーの URL も同期する。

## 6. Service Worker（端末への保存）

`docs/sw.js` は `build_web_map.py` が生成する（手で編集しない）。取得したファイルをその場で保存する方式で、先読みで二重に落とさない。
- 詳細データ（`shards/*.json`）と座標（`points.bin`）：キャッシュ優先。キャッシュ名にデータ版（共有シャードと各ビューの points.bin の
  内容ハッシュ）を含め、データが変わると sw.js が変わって新しい Worker が入り、古いキャッシュを捨てる。
- HTML：ネットワーク優先（UI の更新を即反映）、オフライン時はキャッシュ。Plotly CDN・画像：キャッシュ優先。計測は素通し。
- **更新直後の競合**：HTML はネットワーク優先、データはキャッシュ優先なので、データ更新の直後は「新しい HTML ＋ 古い Worker の保存データ」が
  一度だけ起こり得る（v1.3 公開直後にスマホの 2D で points.bin の長さ不一致が出た）。対策として `points.bin?v=<内容ハッシュ>`、
  `shards/NNN.json?v=<内容ハッシュ>` の形で取得する（`M.pointsVer` / `M.shardVer`）。古いキャッシュには当たらず、新しい Worker が
  入れば古いキャッシュごと捨てられる。さらにページ側で points.bin の長さを `M.pointsBytes` と照合し、合わなければ 1 回だけ再取得する。
- 効果：再訪時の通信ゼロ、オフラインでも開く。iOS はホーム画面に追加していないサイトの保存領域を 7 日未使用で消すことがある。
右下の「全データ読み込み完了」は 2 秒で消し、端末保存から 1.5 秒未満で読めた場合は表示しない。

## 7. 球面ビューの描画上の注意

- 裏側の点を隠すために不透明な球（半径 0.985）を置いている。点（半径≈1）との隙間が小さく、しかもブラウザの WebGL 深度バッファは
  **16 ビット**（Chrome・Safari とも実測）で、gl-plot3d の近クリップ面が 0.01 と極端に近い。このため少し縮小しただけで前後判定が崩れ、
  **同心の縞（z-fighting）**が出る。球の半径や点の散らしを固定で変えても、平行投影にしても解消しない。球を距離に応じて縮める方式は
  形状の差し替えで操作が引っかかる。
  対策は**近クリップ面 zNear を視距離に応じて遠ざける**（`glplot.zNear = 0.4×(視距離−1)`、下限 0.02。深度分解能は zNear に反比例）。
  数値を 1 つ変えるだけで軽く、寄ったときも最近接の点より手前に置くので欠けない。
- 点を不透明にすると gl-scatter3d の不透明経路が半透明の 3〜6 倍遅い。半透明にすると重なりの最上層が描画順に偏るので、
  乱数で組に分けて描画順を回転させる（§3）。
- 検証はヘッドレスでも **Metal で GPU を使う**（`--use-angle=metal --enable-gpu --ignore-gpu-blocklist`）。
  swiftshader は深度精度が違い、z-fighting の再現に使えない。

## 8. 検証

UI 変更は **ヘッドレス Chrome（puppeteer-core、iPhone エミュレーション）で回帰確認**してから公開する。
swiftshader は描画が遅く、CDP 経由のタッチイベントは実機とかけ離れた時刻列になるので、
慣性のような時間依存の検証はページ内で合成 TouchEvent を発行する。停止時間など絶対値は実機でしか測れない。
- 時間依存の検証（慣性、フライ・トゥ）はページ内で合成 TouchEvent を発行する。CDP のタッチ API は swiftshader の遅さで実機と
  かけ離れた時刻列になる。減衰の秒数など絶対値は実機でしか測れない。
- ハーネスはセッションの scratchpad に置く（`ptest/*.js`）。

## 9. 運用（版管理・データ更新・計測）

- **版管理**: `CHANGELOG.md` に変更を書き溜め、区切りで git タグ `vX.Y` と GitHub Release を切る（Y＝機能・UI、X＝地図データの更新）。
  サイト上にバージョンは表示しない。
- **データ更新の手順**: 座標 parquet を更新したら **3 ビューすべてを `build_web_map.py` で再生成してから commit** する。
  `docs/shards/` と `docs/sw.js` は生成物で、sw.js のデータ版（共有シャードと各ビューの points.bin の内容ハッシュ）は最後の生成で確定する。
  データが変わると Service Worker が新しい版を入れて古い保存を捨てる。
- **公開反映**: commit 後に `git push`（GitHub Pages、master の `/docs`）。反映まで数分。Cache-Control は 10 分固定。
- **計測**: GoatCounter（`rma-lab.goatcounter.com`）で閲覧数のみ。Cookie なし。
- **Search Console**: ルート `https://rma-lab.github.io/` を URL プレフィックスで登録済み（確認ファイルは玄関ページのリポジトリ）。
- **生成スクリプトの JS の注意**: `setupUI` 関数内で `var x = null;` と宣言した変数は、それより前（main や setupUI 冒頭）の代入を
  巻き上げで上書きする。setupUI 内で使う状態はトップレベルで宣言するか、初期化子なしの `var` にする。

## 10. 既知の制約

- **Plotly の限界**：トレース 255 本、不透明点の遅さ、タッチ非対応。R10 のウェブアプリでは deck.gl 系への移行が本命。
- **転送量**：GitHub Pages の目安 100GB/月に対し 1 閲覧 20MB なので月 5,000 閲覧程度が上限。
- iOS はホーム画面に追加していないサイトの保存領域を 7 日間未使用で消すことがある（PWA として追加すれば残る）。
- SNS のプレビュー画像は URL ごとに変えられない（静的サイト）。課題の URL でもカードは共通の画像とサイト名になる。
